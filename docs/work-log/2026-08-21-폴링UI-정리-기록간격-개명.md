# 작업 보고서 - 폴링 UI 정리 + "주기" → "기록 간격" 개명

**날짜**: 2026-08-21
**Phase**: Phase 1 (UI 완성)
**작업자**: Claude Code
**관련**: [ADR-0019](../decisions/0019-수집주기-단일출처-기록간격-용어분리.md), [설계 스펙](../superpowers/specs/2026-08-21-reporting-autoupdate-rx-accuracy-design.md)

## 작업 목표

아무 동작도 트리거하지 않던 헤더의 `다음 폴링 mm:ss` 카운트다운을 걷어내고, 화면이 실제 동작(60초 고정 수집)을 그대로 드러내게 한다. 아울러 오해를 부르던 "주기"를 "기록 간격"으로 개명한다.

## 배경

사용자 문의: `1440:58` 이라는 표시가 무엇이냐, 그리고 **"주기는 사실상 겉치레 아니냐, 어차피 1분마다 보내는데."**

추적 결과 세 결함이 겹쳐 있었다.

1. 카운트다운이 0에 도달해도 **아무것도 하지 않았다** — `usePolling` 은 값만 되감았고, 실제 수집은 `App.jsx` 의 별개 60초 타이머였다.
2. 카운트다운이 **`nodes[0]` 한 대의 주기만** 보고 그려졌다.
3. `mmss()` 가 시(hour) 단위로 올리지 않아 1일(1440분) 주기에서 86400초가 `1440:58` 로 찍혔다. 값은 맞고 표기가 틀렸다.

사용자 지적은 절반 맞다. 전송 빈도로서는 무의미하지만, `receptionOf` 가 이 값으로 지연·끊김을 가르므로 **판정 기준으로는 실동작**한다. 그래서 "제거"가 아니라 **"분리"** 로 갔다.

## 구현된 기능

- 헤더가 **실제 수집 주기**를 표시한다 (`1분마다 자동 확인`). 타이머와 문구가 같은 상수를 읽어 구조적으로 어긋날 수 없다.
- 마지막 확인 시각을 상대시간으로 표시하고 10초마다 갱신한다.
- **`지금 전송`** — 1분을 기다리지 않고 즉시 확인·전송. 없으면 `새로 보낼 측정값이 없습니다` 토스트.
- `기록 간격` 개명 + 보조 문구로 "수집 빈도가 아니라 판정 기준"임을 화면에서 드러냄.

## 알려진 이슈

- **전 노드의 기록 간격이 1440분(위저드 기본값)** 이라 판정 임계가 36시간(지연)/72시간(끊김)이다. **이틀 무수신도 "수신중"으로 표시된다.** 실제 기록 간격에 맞춰 조정해야 알림이 제때 뜬다.
- `lastSyncAt` 은 메모리에만 있다 — 재시작하면 "확인함" 표시가 사라진다 (Phase 2 SQLite 이관 대상).
- 수집 주기는 여전히 고정 60초다. 노드별 기록 간격에 맞춰 조절하지 않는다. 누적형 파일이 유입되면 재검토 필요.
