# 0019. 수집 주기를 단일 출처로 고정하고 "주기"를 "기록 간격"으로 분리한다

- 상태: 채택됨
- 날짜: 2026-08-21
- 결정자: 사용자 / Claude Code
- 관련: [ADR-0005](0005-수신-신선도-모니터링.md), `docs/superpowers/specs/2026-08-21-reporting-autoupdate-rx-accuracy-design.md`, `src/lib/store.jsx`, `src/pages/NodeMonitor.jsx`

## 맥락

사용자가 노드 모니터 헤더에서 `다음 폴링 1440:58` 이라는 표시를 보고 "이게 무슨 케이스냐"고 물었다. 추적한 결과 "주기"라는 이름이 붙은 값이 넷이었고, 서로 연결되어 있지 않았다.

| 이름 | 위치 | 실제 역할 |
|---|---|---|
| 노드 `intervalMin` ("수신 주기") | 등록 위저드 | 지연/끊김 판정 + 백엔드 `report_interval_min` |
| 실제 수집 주기 | `App.jsx` | **60초 하드코딩.** 노드 주기와 무관 |
| 헤더 "다음 폴링" | `NodeMonitor.jsx` | `nodes[0].intervalMin * 60` 카운트다운 |
| `POLL_INTERVAL_SEC` | `theme.js` | 아무도 안 씀. 값도 1시간으로 틀림 |

세 가지 결함이 겹쳐 있었다.

1. **카운트다운이 아무것도 트리거하지 않았다.** `usePolling` 은 0에 도달하면 값만 되감았다(`s <= 0 ? intervalSec : s - 1`). 실제 수집은 별개의 60초 `setInterval` 이 담당한다. 사용자에게는 "이 시계가 다 돌면 파일을 읽는다"로 읽히지만 둘 사이에 연결이 없다.
2. **카운트다운이 `nodes[0]` 하나만 봤다.** 노드가 여러 대여도 첫 노드의 주기로만 그렸다.
3. **`mmss()` 가 시(hour) 단위로 올리지 않았다.** 1일(1440분) 주기에서 86400초가 `1440:58` 로 찍혔다. 값은 맞고 표기가 틀렸다.

사용자 지적: **"주기는 그러면 사실상 겉치레잖아? 어차피 매번 1분마다 보내는데."**

절반 맞다. 전송 빈도로서는 무의미하다. 그러나 `receptionOf`(`lib/reception.js`)가 이 값으로 live/delayed/lost 를 가르므로 판정 기준으로는 실동작한다. 그리고 향후 일일 보고·즉시 알림의 발동 조건이 이 판정에 종속된다.

핵심 질문: **표시를 고칠 것인가, 개념을 분리할 것인가.**

## 결정

**개념을 분리하고, 각각을 단일 출처로 고정한다.**

1. **수집 주기** — `lib/store.jsx` 에 `SYNC_INTERVAL_MS = 60_000` 을 두고 `App.jsx` 의 타이머와 화면 문구가 **같은 상수를 읽게** 한다. 둘이 갈라질 수 없게 만든다.
2. **가짜 카운트다운 제거** — `usePolling` 훅을 삭제하고, 헤더는 실제 사실만 표시한다: `1분마다 자동 확인 · N분 전 확인함`. "마지막 확인 시각"은 `syncAll()` 이 완료될 때마다 스토어의 `lastSyncAt` 에 찍는다(보낼 게 없었어도 찍는다 — 자동 확인이 살아있다는 증거).
3. **`주기` → `기록 간격`** 전면 개명. 이 값은 *장비가 값을 기록하는 간격*이며, 수집 빈도가 아니라 **지연·끊김 판정 기준**임을 이름과 보조 문구로 드러낸다.
4. **`지금 전송` 버튼 추가** — 1분을 기다리지 않고 즉시 확인·전송. 가짜 카운트다운이 제공하던 "언제 되나" 심리적 기능을 진짜 기능으로 대체한다.
5. **`POLL_INTERVAL_SEC` 삭제** — 미사용 + 값이 틀림.

## 결과

**좋은 점**

- 화면에 표시되는 주기와 실제 동작이 구조적으로 어긋날 수 없다(같은 상수).
- 노드 수와 무관하게 동작한다. `nodes[0]` 의존 제거.
- `1440:58` 표기 버그가 카운트다운 제거로 자연 소멸 — `mmss()` 를 고칠 필요가 없어졌다.
- "기록 간격"이 판정 기준임이 드러나, 후속 알림 작업에서 이 값을 정확히 설정해야 할 이유가 사용자에게 보인다.
- 사용자가 결과를 1분 기다리지 않고 확인할 수 있다.

**트레이드오프**

- 수집 주기가 여전히 고정 60초다. 노드별 주기에 맞춰 수집 빈도를 조절하지 않는다. 파일 재읽기가 저렴하고(덮어쓰기 방식이라 파일이 커지지 않는다는 전제) 증분 전송이 워터마크 기반이라 현재는 문제되지 않는다. 누적형 파일이 유입되면 재검토한다.
- `lastSyncAt` 은 메모리에만 있다. 재시작하면 "확인함" 표시가 사라진다(Phase 2 SQLite 이관 대상).

**후속**

- 전 노드의 기록 간격이 1440분(위저드 기본값)이라 판정 임계가 36시간(지연)/72시간(끊김)이다. **이틀 무수신도 "수신중"으로 표시된다.** 실제 노드별 기록 간격에 맞춰 조정해야 알림이 제때 뜬다.
- 알림 작업(일일 보고·즉시 알림) 착수 전에 "마지막 수신" 값 자체를 데이터 시각 기준으로 바로잡아야 한다(별도 작업). 지금은 파일 저장시각이라 판정이 틀린다.

## 대안

- **표기만 고치기(`mmss()` 를 시:분:초로).** `1440:58` → `23:59:58` 이 되어 증상은 사라지지만, 카운트다운이 아무것도 트리거하지 않는다는 본질과 `nodes[0]` 의존은 그대로 남는다. 사용자가 "겉치레"라고 부른 것이 정확히 이 지점이라 채택하지 않았다.
- **수집 주기를 노드별 `intervalMin` 에 맞추기.** 카운트다운을 진짜로 만들 수 있다. 그러나 노드마다 타이머가 생겨 복잡해지고, 얻는 이득(파일 재읽기 절약)이 현재 규모에서 미미하다. 누적형 파일이 유입되면 재검토한다.
- **"주기" 이름 유지.** 기존 문서·스크린샷과의 일관성은 지키지만, 이 오해가 바로 이번 문의의 출발점이었다.
