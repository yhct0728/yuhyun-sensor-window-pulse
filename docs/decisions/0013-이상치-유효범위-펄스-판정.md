- 상태: **폐기됨 ([ADR-0014](0014-정상범위-폐기-고장-임계값-두-축.md) 로 대체됨, 2026-06-05)**

> ⚠️ **폐기 사유(2026-06-05 같은 날)**: 백엔드가 valid_min/max/spike 계약을 되돌리고, 품질을 **고장(dead) + 임계값(level)** 두 축으로 재정의함. 본 ADR 의 정상범위(valid_min/max) 로컬 판정·백엔드 전송은 전부 제거됨. 자세한 새 모델은 ADR-0014 참조.

## 맥락

로우데이터에 물리적으로 불가능한 값(예: 수위계 12.8m, 균열계 8000mm)이 섞여 들어온다. 이를 거르려면 "이 센서는 이 범위 안의 값만 정상"이라는 **유효범위 기준**이 필요하다.

ADR-0010(및 메모리에 못박힌 원칙)은 "Pulse = 정직한 raw 전송, 이상치·품질 판정 = 백엔드(GeoMonitor) 전담"이었다. 그러나 운영 요구상 **수집기(Pulse) 화면에서 센서별 유효범위를 직접 설정하고, 벗어난 값을 즉시 눈으로 확인**할 수 있어야 한다는 결정이 내려졌다. 핵심 질문: 유효범위를 어디에 보관하고 누가 판정하는가.

## 결정

**Pulse 가 센서(채널)별 유효범위를 보관하고, 전송하는 raw 값과 대조해 이상치 여부를 판정·표시한다.**

- 설정 단위: 센서(채널) **개별 입력**(노드 상세 드로어). 종류별 기본값 페이지는 두지 않는다.
- 판정은 순수 함수 단일 소스 `lib/outlier.js`(`isOutlier`, `nodeOutlierCount`)에서만. 경계 포함(>=min, <=max 정상), 범위 미입력/결측이면 검사하지 않음.
- **비파괴(표시 전용)**: 범위를 벗어나도 값을 버리거나 0/보정하지 않는다 — raw 보존(`value:null` 보존 원칙과 일관). 🔴 이상치 표식만 드로어 채널 행 + 노드 목록 요약 배지에 붙인다.
- 저장: 임시 localStorage(`pulse:channelRanges`), Phase 2 에서 SQLite 로 이관.

## 결과

- 좋은 점: 운영자가 수집 단계에서 명백한 이상치를 즉시 인지. 값 변형이 없어 원본 무결성·백엔드 정본 판정과 충돌하지 않음.
- 트레이드오프: ADR-0010 의 "판정=백엔드" 원칙을 일부 변경 — 단, 펄스의 판정은 **표시 보조**이고 정본 품질 판정은 여전히 백엔드와 병행한다(전송값 자체는 불변).
- 후속: 종류별 기본값(템플릿), 다단계 경고/주의 등급은 추후 별도 결정.

### 갱신 (2026-06-05, 같은 작업 내)

범위의 **백엔드 전송**을 같은 날 추가로 구현했다(원안의 "로컬에만 보관"에서 확장). 백엔드 확정 계약: **별도 API 가 아니라 노드 등록(`POST /api/pulse/v1/nodes`)을 같은 `node_code` 로 다시 보내** 기존 센서의 `valid_min`/`valid_max`(raw 기준)를 갱신(sticky). 드로어 "정상범위 저장" 버튼이 화면값 그대로(WYSIWYG, 미입력=null=해제) 최소 본문으로 전송하며 **`sensor_sync` 는 보내지 않는다**(additive 기본 — 다른 센서 무영향). 구현: `backendApi.nodeRangeBody`/`bareSensorCode`, IPC `nodes:set-ranges`, `store.saveChannelRanges`. localStorage 는 로컬 표시 캐시로 유지(백엔드가 정본).

## 대안

- **백엔드/웹에만 두기**(ADR-0010 유지): 수집 단계 즉시 확인이 불가해 운영 요구를 못 채움 — 기각.
- **펄스가 이상치 값을 드롭/보정**: 원본 무결성·`value:null` 보존 원칙과 충돌 — 기각(표시만 채택).
- **종류별 기본값 + 개별 예외 2단 구조**: 더 편하지만 범위가 커짐 — 이번엔 개별 입력만(YAGNI), 추후 확장 여지로 남김.
