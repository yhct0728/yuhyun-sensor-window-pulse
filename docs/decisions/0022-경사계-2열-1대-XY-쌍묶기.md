# 0022. 경사계는 값 열 2개를 1대(X·Y)로 묶어 일반 값 센서로 등록한다

- 상태: 채택됨
- 날짜: 2026-10-12
- 결정자: 사용자 / Claude Code
- 관련: `src/lib/sensorModel.js`, `src/lib/instrumentCatalog.js`, `tests/tilt-pairs.spec.js`, [ADR-0018](0018-채널코드-접두가-채널종류를-따라감.md), CHANGELOG `[Unreleased]`

## 맥락

구조물 경사계 파일은 한 파일에 값이 4개 또는 6개 들어온다. 현장 확인 결과 **값 2개가 경사계 1대의 X·Y** 다(4개 = 2대, 6개 = 3대).

기존 코드는 다르게 가정했다. 경사계 1대가 A0·A180·B0·B180 네 값을 내고, 1·2열이 X, 3·4열이 Y 라고 봤다(수동 계측 보고서 양식에서 온 가정). 그래서 세 가지가 틀렸다.

1. 4값 파일을 2대가 아니라 1대로 묶었다.
2. 6값 파일은 5·6열을 경고 없이 버렸다.
3. 묶은 값을 `raw_channels` 로 보냈는데, 백엔드 ingest 는 `value` 만 읽는다(백엔드 `main` 에 `raw_channels` 처리 없음). 서버가 값을 읽지 못했다.

## 결정

경사계(`tilt`)는 **값 열마다 일반 값 센서 1개**로 등록하고, **열 2개씩 1대로 묶어 코드에 대 번호와 축을 붙인다.**

- 코드: `BT-{대 번호}-{X|Y}` — 4열이면 `BT-1-X`, `BT-1-Y`, `BT-2-X`, `BT-2-Y`.
- 전송: 다른 계측기와 같은 `value`. `raw_channels` 를 쓰지 않는다.
- 묶는 조건: 온도열을 뺀 값 열이 전부 경사계이고 개수가 짝수일 때.
- 홀수 열이거나 종류가 섞이면 묶지 않고 열마다 센서로 둔다(`BT-1`, `BT-2`…). 홀수 열은 등록 화면에 경고를 띄운다. 값은 어느 경우에도 버리지 않는다.
- 열 순서는 X1, Y1, X2, Y2… 로 본다(추정 — 로거 설정이 다르면 파일에서 확인 필요).

`instrumentCatalog` 의 `tilt` 항목(형제 분할)은 지웠다. 규칙은 `sensorModel.js` 한 곳에 있다.

## 결과

**좋은 점**

- 백엔드를 고치지 않는다. 서버는 임의 센서 코드와 `value` 를 이미 받는다.
- 6값 파일의 모든 열이 올라간다.
- 서버 화면에서 이름만 봐도 어느 대의 어느 축인지 안다.

**감수하는 점**

- 서버와 웹은 X·Y 를 별개 센서로 본다. 묶음은 이름으로만 드러난다. 한 그래프에 같이 그리거나 한 대로 판정하려면 웹·서버 작업이 따로 필요하다.
- 옛 방식(`BT-X`, `BT-Y`)으로 등록된 경사계 노드는 **삭제 후 다시 등록해야** 한다. 서버 센서 코드가 달라 전송이 "재전송"에 머문다. 등록된 노드에는 재등록 버튼이 없어 노드 상세의 "노드 삭제"를 거쳐야 하고, 삭제하면 그 노드의 서버 데이터도 지워진다. 현장에 배치된 노드는 웹에서 회수한 뒤에만 삭제된다.

**후속**

- 다른 `raw_channels` 계측기(하중계·진동계·지진계·간극수압계·광파타겟·풍향풍속·온습도)도 같은 이유로 서버가 값을 못 읽을 수 있다. 별도 확인 필요.

## 대안

- **앞면·뒷면 쌍(A0−A180)으로 계산** — 현장 확인으로 기각. 6값 파일을 설명하지 못하고, 빼기 계산을 서버에 새로 만들어야 한다.
- **서버에 X·Y 묶음 개념 추가** — 지금 필요한 건 값이 올바른 이름으로 올라가는 것이다. 묶어서 보여 달라는 요구가 생기면 그때 한다.
