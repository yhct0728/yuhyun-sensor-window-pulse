# 0001. 아키텍처 문서화에 ADR + C4 + Changelog 채택

- 상태: 채택됨
- 날짜: 2026-05-25
- 결정자: 사용자 / Claude Code
- 관련: [CHANGELOG.md](../../CHANGELOG.md), [docs/architecture/](../architecture/)

## 맥락

작업이 즉흥적이든 계획적이든 코드 수정·기획 피드백이 계속 쌓이는데, 이를 **타팀에 보고**할 일관된 체계가 없었다. 기존엔 `docs/work-log/`(작업 단위 보고서), `CLAUDE.md`(상태 문서), 세션 메모리에 흩어져 있었고, 가벼운 즉흥 변경은 어디에도 안 남았다.

요구사항:

- 목적은 **타팀 보고**.
- **의미 있는 결정만** 남긴다 (오타·리네이밍 제외).
- **매번** 기록한다.
- 기록이 길어져도 **읽기 부담이 없어야** 한다.
- 단순 md 나열이 아니라 **아키텍처 전체가 시각적으로** 보였으면 한다.

## 결정

세 가지를 역할별로 나눠 도입한다.

- **ADR** (`docs/decisions/`) — "왜 그렇게 정했나". 결정 1건 = 파일 1개, 불변, 인덱스로 관리.
- **CHANGELOG.md** (Keep a Changelog) — "무엇이 바뀌었나". 타팀 보고용 다이제스트.
- **C4 모델** (`docs/architecture/`) — "전체가 어떻게 구성되나". **LikeC4**(인터랙티브 웹뷰) + **Mermaid**(문서 인라인) 병행.

읽기 부담은 **점진적 공개**로 해결한다: ADR은 인덱스+원자적 파일, C4는 Context→Container→Component 줌 레벨.

## 결과

- 좋은 점: 결정의 근거가 한 곳에 누적되고, 보고는 CHANGELOG 링크 하나로 끝난다. 아키텍처는 레벨별로 분해돼 신규 인원도 빠르게 파악.
- 트레이드오프: 의미 있는 결정마다 ADR+CHANGELOG 한 줄을 **매번 챙겨야** 한다(규율 비용). C4 모델은 코드와 따로 관리되므로 구조가 크게 바뀌면 갱신해야 한다.
- 후속: 이후 의미 있는 변경은 이 절차를 따른다. `docs/work-log/` 의 상세 보고서 체계는 그대로 두고 병행(작업 단위 vs 결정 단위).

## 대안

- **work-log 보고서만 유지** — 작업 단위라 즉흥 변경/결정 단위를 못 담고, 타팀 보고엔 무겁다.
- **git 커밋 + Conventional Commits 자동 생성** — 좋지만 이 프로젝트는 아직 git 저장소가 아니라 보류. 도입 시 CHANGELOG 자동화로 확장 가능.
- **단일 CHANGELOG 한 파일** — 가볍지만 "왜"의 맥락을 담기 어려워 ADR을 함께 둠.
