# 설계: 수신 정확도 · 자동 업데이트 · 일일 보고

- 날짜: 2026-08-21
- 상태: 승인 대기
- 범위: 4개 독립 작업 + 선행 0번. 각각 별도 계획/구현 사이클.

## 배경

사용자 보고 두 건에서 출발:

1. 메모장(.txt) 안에서 데이터가 끊긴 시점과, 앱 화면의 "마지막 수신" 날짜가 일치하지 않음.
2. 화면의 "다음 폴링" 카운트다운이 `1440:58` 로 표시됨.

코드 추적 결과 둘 다 실제 결함으로 확인됨. 여기에 사용자 요구 두 건(일일 보고, 자동 업데이트)이 추가되어 총 4개 작업으로 분해함.

## 확인된 사실 (코드 근거)

### F1. `lastRx` 의 의미가 경로마다 다름

| 경로 | 코드 | 들어가는 값 |
|---|---|---|
| 노드 등록 | `src/components/nodes/RegisterWizard.jsx:131` | 파일 저장시각(OS mtime) |
| 자동 임포트 | `src/lib/store.jsx:587` | 파일 저장시각(OS mtime) |
| 백엔드 복원 | `src/lib/store.jsx:340` ← `src/lib/backendApi.js:295` | 백엔드 `last_seen` |
| 전송 성공 직후 | `src/lib/store.jsx:457` | **데이터 행의 마지막 시각(maxTs)** |

기본값은 파일 저장시각이며, 전송이 성공한 노드만 데이터 시각으로 바뀐다. 결과적으로 같은 화면에서 노드마다 기준이 섞인다.

추가로 `src/lib/store.jsx:379` 에서 신규 행이 없으면 조기 return 하므로, 끊긴 노드는 등록 당시 mtime 이 영구히 박제된다.

타사 로거는 파일을 덮어쓰므로 데이터가 끊겨도 mtime 은 갱신될 수 있다. 즉 "끊긴 노드가 정상으로 보이는" 방향의 오류다.

### F2. "주기"라는 이름이 4개이고 서로 연결되지 않음

| 이름 | 위치 | 실제 역할 |
|---|---|---|
| 노드 `intervalMin` ("수신 주기") | 등록 위저드 | 수신중/지연/끊김 판정 + 백엔드 `report_interval_min` 저장 |
| 실제 스캔 주기 | `src/App.jsx:70` | **60초 하드코딩.** 노드 주기와 무관 |
| 화면 "다음 폴링" | `src/pages/NodeMonitor.jsx:44` | `nodes[0].intervalMin * 60` 카운트다운. 아무것도 트리거하지 않음 |
| `intervalGuess` | `src/folderService.js:267` | 앞 두 행 시각 차이. 위저드 기본값 채움용 |

카운트다운이 0에 도달해도 아무 동작이 없다 (`src/hooks/usePolling.js:35` — 값만 되감김).

`1440:58` 의 원인: 등록 위저드 기본 주기가 1일(`RegisterWizard.jsx:28` `DEFAULT_INTERVAL = 1440`)이고, `mmss()`(`NodeMonitor.jsx:18`)가 시(hour) 단위로 올림하지 않아 86400초를 `1440:58` 로 표시한다. 값 자체는 정확하나 표기가 틀렸다.

### F5. 파싱 흐름

**등록 시 1회** (`analyzeFile`, `src/folderService.js:250`): 인코딩 판별(BOM) → 구분자 판별(첫 줄, 쉼표/탭/세미콜론 최빈) → **앞 10줄만** 미리보기 → `resolveSensors` 로 열↔센서 매핑 확정.

**60초마다** (`readMeasurements`, `src/folderService.js:509`): 파일 전체 재읽기 → 인코딩·구분자 재판별 → 헤더 판정(첫 행 둘째 칸부터 비숫자 존재 시 제목) → 전 행 파싱 → 0열을 시각으로 파싱(실패 행 폐기) → `ts > lastSentTs` 인 행만 전송.

값 규칙: 빈 칸 → `null`(결측, 전송함) / 비숫자 → `null` / 열 자체 없음 → 스킵 / 온도 열 → 센서 아님(부속).

**알려진 취약점:**
- (a) 등록 판정이 앞 10줄 표본에만 근거 — 파일 중간 형식 변화 미감지
- (b) 60초마다 파일 전체 재읽기 — 누적형 파일이 있으면 선형 증가
- (c) 구분자를 첫 줄 하나로 결정 — 제목 줄에 쉼표 혼입 시 오판
- (d) **전송 타임스탬프에 시간대 표기 없음** — `store.jsx:22 toIso()` 가 벽시계 그대로 유지(`2026-05-20T14:00`). 백엔드가 KST 로 읽는지 UTC 로 읽는지에 따라 9시간 편차. **백엔드 확인 필요(미해결)**

## 결론: 파싱은 정상. 백엔드 주소 오설정이 원인.

### D-1. 백엔드 URL 오설정 (전송 중단의 직접 원인)

`%APPDATA%/pulse/pulse-config.json` (수정일 2026-06-02):

```

```

실제 주소로 검증:

```
https://yuhyun-sensor-back-5yh6.onrender.com
  GET /api/pulse/v1/status  (인증 없이) → 401 "No token provided"  = 서버 생존
  GET /api/pulse/v1/nodes   (기존 키)   → 200 OK                   = 키도 유효
```

**기존 API 키는 그대로 유효하다.** URL 만 교체하면 전송이 복구된다.

`ingestToBackend` 는 네트워크 실패 시 `{ok:false, error:'network'}` 를 반환하고
(`src/folderService.js:563`), `syncNode` 는 `allOk=false` → `transmit:'retry'` 로
버퍼에 누적한다(`src/lib/store.jsx:457`). 즉 데이터 유실은 아니고 재전송 대기 상태.

### D-4. 80053 — 동일 노드 ID 이중 소스 (최초 문의의 원인)

